# StayUp — 機能設計書

## 1. 背景と目的

MacBook のふたを閉じた状態でも coding agent（Claude Code, Codex CLI など）を走らせ続けたい。
macOS はふたを閉じるとクラムシェルスリープに入り、長時間タスクが中断される。

既存の [`awake.sh`](../../nixos-config/modules/home/base/programs/awake.sh) は CLI としてこの課題を解決しているが、以下の不満がある。

- ターミナルを開いていないと状態がわからない / 操作できない
- `sudo` 認証やバックグラウンドプロセスの管理が煩雑
- 「今 awake が効いているか」が一目でわからない
- 解除し忘れて、気づいたら一晩中スリープしていなかった

**StayUp** は、この awake 相当の機能をネイティブ macOS アプリとして提供する。
常時の視認性（メニューバー）、詳細操作（ウィンドウ）、プログラムからの制御（CLI）の 3 つの導線を持つ。

### ゴール

- ふたを閉じても Mac をスリープさせない状態を、GUI から 1 クリックで開始・停止できる
- **外部プロセスが CLI を通じて、必要な間だけ抑止を要求できる**。
  人間が「これから長いタスクを流すから」と先回りして操作しなくてよい
- 現在誰が抑止を要求しているかが常に見える
- **解除し忘れを構造的に防ぐ**（TTL・バインド・グローバル拒否権・フェイルセーフ）

### 設計原則: 汎用性

coding agent は本アプリを作る**動機**ではあるが、**設計に持ち込まない**。

> StayUp は「スリープ抑止を要求する任意のクライアント」を平等に扱う。
> インターフェースにも実装にも、特定のツール（Claude Code, Codex CLI 等）の名前・
> 設定ファイル形式・ライフサイクルに関する知識を一切持たせない。

具体的には：

- CLI の語彙は `acquire` / `renew` / `release` / `run` という**リース操作の一般語**のみ。
  `--owner` は自由文字列で、アプリはその中身を解釈しない
- 特定ツールの設定ファイルを書き換えるコマンド（フックの自動インストール等）は**作らない**
- ビルドスクリプト、CI、`make`、動画エンコード、バックアップなど、
  coding agent と同じ資格でリースを取れる

特定ツールとの繋ぎ込み方は**付録の利用例**として文書で示す。実装には入れない（付録 A）。

### 非ゴール

- ディスプレイの常時点灯（デフォルトでは画面はスリープさせる。省電力・焼き付き防止のため）
- リモートからの起動（Wake on LAN 等）
- クライアントプロセス自体の起動・管理・監視
- 特定ツールの設定ファイルの読み書き
- **コントロールセンターへの常駐**（後述）

### スコープ外とした導線: コントロールセンター

macOS 26 ではサードパーティも Control Center にコントロールを追加できるが、
**初期リリースでは実装しない**。

- サードパーティが作れるのは `ControlWidgetButton` と `ControlWidgetToggle` のみで、
  展開パネル（おやすみモードのように押し込んで候補を選ぶ UI）の API は公開されていない。
  結局「単なる ON/OFF ボタン」にしかならず、メニューバーに対する優位が小さい
- ウィジェット拡張はホストアプリとは別プロセスになるため、状態共有（App Group）と
  更新（`reloadControls`）の経路が増える。コア機能が固まる前に持ち込む複雑さに見合わない
- 「即時にトグルしたい」という価値はグローバルホットキーで満たせる

`AppIntent` は実装するので、Shortcuts からは操作できる（§8.3）。
コントロールセンター対応が必要になっても、その `AppIntent` を `ControlWidget` で包むだけで済む。
**将来の追加を妨げない形にしておく**のがここでの設計上の要件。

## 2. 用語

| 用語 | 定義 |
| --- | --- |
| **リース** | 「スリープを抑止せよ」という要求の 1 単位。所有者・TTL・バインド対象を持つ |
| **クライアント** | リースを要求する主体。GUI 自身と、CLI 経由の任意の外部プロセスの両方を指す |
| **抑止期間** | 有効なリースが 1 つ以上あった連続区間。実際に `pmset` を触っていた時間 |
| **クラムシェルスリープ** | ふたを閉じたときに走るシステムスリープ。`pmset disablesleep` でのみ抑止できる |
| **アイドルスリープ** | 一定時間無操作で走るシステムスリープ。`IOPMAssertion` で抑止できる |
| **アサーション** | `IOPMAssertionCreateWithName` で作る電源管理の宣言。プロセス単位で、プロセス死亡時に自動解放される |
| **ヘルパー** | root 権限で `pmset` を実行する常駐 LaunchDaemon |
| **バインド** | リースの生存を外部の存在（PID・ファイル）に紐づけること。対象が消えたらリースも消える |

## 3. スリープ抑止の技術的前提

これが設計全体を決める制約なので先に整理する。

| やりたいこと | 手段 | root 必要 | プロセス死亡時 |
| --- | --- | --- | --- |
| アイドルスリープ抑止 | `IOPMAssertionCreateWithName(kIOPMAssertPreventUserIdleSystemSleep)` | 不要 | **自動解放** |
| ディスプレイスリープ抑止 | `IOPMAssertionCreateWithName(kIOPMAssertPreventUserIdleDisplaySleep)` | 不要 | **自動解放** |
| ディスク省電力抑止 | `kIOPMAssertPreventDiskIdle` | 不要 | 自動解放 |
| **クラムシェルスリープ抑止** | `pmset -a disablesleep 1` | **必要** | **残留する（危険）** |

重要なのは最後の行。`disablesleep` はシステム全体のグローバル設定で、設定したプロセスが死んでも **1 のまま残る**。
残留すると「ふたを閉じてもスリープしない Mac」が誰にも管理されない状態で放置され、カバンの中で発熱・バッテリー消費する。

したがって本アプリの設計上の最重要要件は：

> **どんな終わり方（正常終了 / クラッシュ / 強制終了 / ログアウト / 電源断）をしても `disablesleep` が 0 に戻ること。**

`awake.sh` は「FIFO の EOF を root ヘルパーが検知して復元する」という方法でこれを実現している。
本アプリでは **XPC 接続の切断検知** で同じ性質を得る（後述 §6）。

### コンポーネント責務

| コンポーネント | 責務 |
| --- | --- |

| `LeaseRegistry` | リース台帳。取得/更新/解放/失効を直列化し、所有者ごとの権限を判定する |

| `ControlSocket` | CLI 用の UNIX ドメインソケットサーバ。接続元 UID を検証し、リクエストを `SessionManager` に委譲 |

| `SessionStore` | リース履歴・監査ログ・設定の永続化 |
| `ClientPolicy` | 外部クライアントからのリクエストの承認判定（許可リスト、上限、承認モード） |
| `StayUpHelper` | root 権限操作の唯一の実行点 |

### 技術スタック

- Swift 6 / SwiftUI / Swift Concurrency（`SessionManager` は `@MainActor` の Observable）
- `MenuBarExtra`（menu スタイル + カスタムビュー）
- `SMAppService.daemon` によるヘルパー登録
- `AppIntents`（Shortcuts / ホットキー / URL スキームの共通の入口）
- 最小要件: **macOS 26.0**

**なぜ macOS 26 を最小要件にするか**

UI を可能な限り標準コンポーネントで組み、**Liquid Glass に自動で追従させる**ため。

- 下位バージョンを支えると、素材・角丸・余白を自前で持つことになり、
  「標準に任せる」という方針そのものが崩れる。条件分岐した見た目を 2 系統保守したくない
- メニューバーのポップオーバーとウィンドウが本アプリの UI のほぼ全てで、
  そこは標準コンポーネントだけで十分に組める。独自描画に逃げる理由がない
- 個人利用が出発点のツールであり、旧 OS を支える必然性が薄い

**トレードオフ**: 配布対象は macOS 26 以降に限られる。
これは意図した選択であり、要検証事項ではない。

## 5. リースモデル

### 5.0 なぜ「セッション」ではなく「リース」か

抑止を要求する主体は 1 つとは限らない。

- ユーザーがメニューバーから開始している最中に、外部プロセスが CLI から要求する
- 同じツールを 2 つの作業ディレクトリで並走させる
- 長時間のビルドと、別のバックグラウンドジョブが同時に走る

これを単一のグローバルなオン/オフで扱うと、**片方が終わっただけで全体が解除される**。
そこで StayUp は要求を **リース (lease)** として個別に管理し、

> **有効なリースが 1 つ以上ある間だけスリープを抑止する**

という参照カウント方式を採る。リースの所有者は自分の分だけを解放でき、他人の要求を壊せない。

```swift
struct Lease {
    let id: LeaseID              // ULID。クライアントに返す不透明な識別子
    let client: Client
    let label: String            // UI に出す人間可読な説明。アプリは中身を解釈しない
    let acquiredAt: Date
    var expiresAt: Date?         // TTL。nil（無期限）は .interactive のみ許可
    let binding: Binding?        // 生存を紐づける対象
    var lastRenewedAt: Date
    var renewCount: Int
}

enum Client {
    /// アプリ自身の UI から要求されたもの（メニューバー / ウィンドウ /
    /// ホットキー / Shortcuts）
    case interactive(trigger: Trigger)

    /// CLI 経由の外部プロセス。`name` は --owner で渡される自由文字列で、
    /// アプリは表示・集計・ポリシー適用のキーとして扱うだけ。中身は解釈しない。
    case external(name: String, pid: pid_t)
}

enum Binding {
    case pid(pid_t)          // そのプロセスが消えたら自動解放（kqueue NOTE_EXIT）
    case leaseFile(URL)      // ファイルが消えたら自動解放（FSEvents）
    case processName(String) // 名前でマッチするプロセスが全て消えたら自動解放
}
```

`Client` を 2 ケースに留めるのが重要な点。
「対話的な要求か、外部プロセスからの要求か」だけが**振る舞いの差を生む本質的な区別**であり、
それ以外（どのツールか、どんな用途か）はアプリにとって単なる表示用の文字列でしかない。

**リースの終わり方**

| 事由 | 説明 |
| --- | --- |
| 明示解放 | `stay-up release <id>` / UI からの削除 |
| TTL 失効 | `expiresAt` 到達。更新されなければ自然に消える |
| バインド解除 | `binding` の対象（PID / ファイル）が消滅 |
| 強制失効 | グローバル停止条件（バッテリー・熱）の成立。§7.6 |

### 5.1 状態機械

システム全体の状態は「有効なリース数」の関数として決まる。

```
                リース数 0 → 1
    ┌──────┐ ─────────────────► ┌───────────┐
    │ idle │                    │ activating│
    └──────┘ ◄───────────────── └─────┬─────┘
       ▲       失敗 / 権限拒否          │ 成功
       │                               ▼
       │                         ┌───────────┐
       │                         │  active   │ ◄── リース追加/削除は
       │                         └─────┬─────┘     ここで自己ループ
       │                               │ リース数 1 → 0
       │                         ┌─────▼──────┐
       └──────────────────────── │deactivating│
              復元完了            └────────────┘

    ┌──────────┐
    │ degraded │  ← ヘルパー不在等でアイドル抑止のみ有効な状態
    └──────────┘
```

- 遷移は**リース数が 0 と非 0 の境界を跨いだときだけ**発生する。
  2 個目のリース取得や 2 個中 1 個の解放では `pmset` を叩かない
- **`degraded`**: ヘルパーが未インストール / 通信不能だが、`IOPMAssertion` によるアイドルスリープ抑止だけは効いている状態。
  「ふたを閉じるとスリープします」と明示する。黙って成功したふりをしない
- 状態遷移とリース台帳の更新は `SessionManager` の単一アクター内で直列化する。
  複数クライアントからの同時 acquire/release は競合しない

### 5.2 停止条件

停止条件には**リース単位**のものと**グローバル**のものがある。

```swift
// リース単位: そのリースだけを終わらせる
enum LeaseCondition {
    case ttl(Duration)                     // 時間（更新可能）
    case boundProcessExit(pid_t)           // 紐づけたプロセスの終了
    case boundFileRemoved(URL)             // 紐づけたリースファイルの消滅
}

// グローバル: 全リースを強制失効させる拒否権
enum GlobalStopCondition {
    case batteryBelow(percent: Int)        // バッテリー駆動時のみ評価
    case cpuIdle(threshold: Double, for: Duration)
    case thermalCritical                   // 無効化不可
    case maxTotalDuration(Duration)        // 抑止の総継続時間の上限
}

enum ReleaseReason {
    case explicit, ttlExpired, bindingLost           // リース単位
    case battery, cpuIdle, thermal, maxDuration      // グローバル失効
    case helperLost, appTerminating, systemShutdown, error(String)
}
```

- リース単位の条件は **OR 評価**（どれか 1 つでも満たせばそのリースが消える）
- **グローバル条件はリースより強い**。クライアントが何個リースを持っていようと、
  バッテリー閾値や熱の危険域に達したら全て失効させて復元する。
  外部クライアントに委譲した権限に対する、ユーザー側の拒否権にあたる（§12.4）

## 6. コア機能: スリープ抑止と復元保証

### 6.1 有効化シーケンス

1. `SessionManager.start(conditions:)`
2. `AssertionController` が `kIOPMAssertPreventUserIdleSystemSleep` を作成（+ 設定次第で Display / Disk）
   - この時点でアイドルスリープは止まる。root 不要なので**必ず成功する**
3. `HelperClient` が XPC でヘルパーに `setDisableSleep(true, token:)` を要求
   - ヘルパー未登録なら §6.3 のインストールフローへ
   - 拒否・失敗なら `degraded` 状態で継続（アイドル抑止のみ）
4. 成功したら `active` へ遷移。UI 更新・通知・履歴記録

### 6.2 復元保証（最重要）

多層で守る。

| 層 | 仕組み | カバーする障害 |
| --- | --- | --- |
| 1 | 正常な `stop()` → XPC で `setDisableSleep(false)` | 通常操作 |
| 2 | **XPC 接続の `invalidationHandler` / `interruptionHandler`** をヘルパー側で監視。クライアント接続が全て切れたら無条件に `disablesleep 0` | アプリのクラッシュ・強制終了・SIGKILL |
| 3 | アプリ側 `NSApplicationWillTerminate` / `NSWorkspace.willPowerOffNotification` で明示停止 | ログアウト・再起動 |
| 4 | **ヘルパー起動時の孤児チェック**: `disablesleep == 1` かつ有効なクライアントセッションが無ければ 0 に戻す | 電源断・カーネルパニック後の再起動 |
| 5 | **ウォッチドッグ**: アプリは 30 秒ごとに XPC で heartbeat。ヘルパー側で 90 秒 heartbeat が途絶えたら 0 に戻す | XPC 接続だけ生き残る異常系 |
| 6 | アプリ起動時の所有状態復元: `state.json` に `disableSleepSetAt` があれば自動で 0 に戻し、印がなければ警告だけを出す | 復旧前のアプリ再起動・他ツールとの競合 |

層 2 が本命で、`awake.sh` の FIFO EOF 検知と等価の性質を持つ。
層 4/5 はそのバックアップ。
層 6 は StayUp が 1 にした記録がある場合だけ自動復元するため、他ツールの設定をアプリ起動だけで壊さない。

### 6.3 ヘルパーのインストール

- 初回の「ふたを閉じても」有効化時に、必要性を説明するシートを出してから `SMAppService.daemon(plistName:).register()`
- システム設定 →「ログイン項目と機能拡張」での承認を促す導線（`SMAppService.openSystemSettingsLoginItems()`）
- 登録には Developer ID 署名が必要であり、ad-hoc 署名の開発ビルドでは登録操作を無効にする
- ビルド時にアプリ、CLI、ヘルパーを同じ証明書で署名し、3 バイナリの Team ID が一致することを検証する
- 登録後の通常操作では `sudo` を起動せず、root の LaunchDaemon へ XPC で限定された要求を送る
- **ヘルパーを入れずに使う選択肢を必ず残す**（アイドル抑止のみの `degraded` 運用）。
  外部ディスプレイ接続＋クラムシェル運用なら、そもそも `disablesleep` 不要なケースもある
- アンインストール: 設定画面から `unregister()` + `disablesleep 0` を確実に実行

### 6.4 セキュリティ

- XPC リスナーは `NSXPCListener` の `shouldAcceptNewConnection` で接続元を検証
  - `SecCodeCopyGuestWithAttributes` + `SecCodeCheckValidity` により、Team ID と bundle identifier を要求
  - 検証コードは `audit_token` ベース（PID ベースは PID 再利用攻撃に弱いので使わない）
- ヘルパーが公開する操作は `setDisableSleep(Bool)` / `queryState()` / `heartbeat()` の 3 つのみ。
  任意コマンド実行の口は一切作らない
- ヘルパーは `pmset` を絶対パス `/usr/bin/pmset` で実行し、環境変数を継承しない

## 7. 停止条件

§5.2 の分類に沿って、各条件が**リース単位**（そのリースだけを終わらせる）か
**グローバル**（全リースを強制失効させる）かを見出しに明記する。

### 7.1 時間 / TTL (`ttl`) — リース単位

- プリセット: 30分 / 1時間 / 2時間 / 4時間 / 8時間 / 無期限
- カスタム入力: `1h30m` 形式と分単位のステッパーの両方
- **延長**: メニューから「+30分」「+1時間」。残り 5 分で通知＋延長ボタン
- CLI からは `stay-up renew <id> --ttl 30m` で更新。クライアントはこれをハートビートとして使える（§12.3）
- 無期限（`expiresAt == nil`）は `.interactive` なリースにのみ許可する。
  外部クライアントは TTL 必須で、`maxClientLeaseTTL`（既定 2 時間）で上限を切る
- タイマーは `Date` ベース（`DispatchSourceTimer` の相対時間だけに頼らない。システムスリープを跨いでもズレない）

### 7.2 バッテリー (`batteryBelow`) — グローバル

- 既定 20%、1〜99% で設定可
- **AC 電源接続中は評価しない**（`awake.sh` と同じ）。AC が抜けた瞬間に評価を再開
- 閾値の 5% 上で事前警告通知
- `IOPSNotificationCreateRunLoopSource` によるイベント駆動（ポーリングしない）

### 7.3 バインド (`boundProcessExit` / `boundFileRemoved`) — リース単位

「要求元が終わったら、そのリースだけが自動で消える」ための条件。
release 忘れが構造的に消えるので、**外部クライアント連携では TTL と並ぶ主機構**になる。

| 方式 | 実装 | 用途 |
| --- | --- | --- |
| PID バインド | `kqueue(EVFILT_PROC, NOTE_EXIT)` | `stay-up acquire --bind-pid $$`。最も確実 |
| リースファイル | `FSEvents` でファイル消滅を監視 | 作業ディレクトリ内のファイルに紐づける。ディレクトリごと消えても解放される |
| プロセス名 | 名前でマッチするプロセスが**全て**消えたら解放 | UI からの指定や、PID を取りにくい場合 |

- 呼び出し元のターミナルに紐づけたい場合は、`--bind-pid $PPID` で表現できる。
  「ターミナル連動」という専用の概念は設けない（PID バインドの一用法にすぎない）
- `stay-up run --` は内部的に PID バインドを使う。プロセス終了 = リース終了なので**漏れが原理的に起きない**。
  外部からの利用ではこれを第一候補として案内する（§12.2）
- バインド対象が取得時点で存在しない場合は、リースを作らずエラーを返す（即座に消えるリースを作らない）
- プロセス名バインドには猶予（既定 10 秒）を設ける。対象が再起動するケースの誤検知を避ける

### 7.4 CPU アイドル (`cpuIdle`) — グローバル

- 「CPU 使用率が N% 未満の状態が M 分続いたら全リースを失効させる」
- 既定 OFF。ON 時は 15% / 10 分
- 入力待ちやネットワーク待ちで止まっている間も CPU は下がるので、誤爆しやすい。
  バインドや TTL で足りるケースがほとんどなので、既定 OFF を維持する

### 7.5 熱状態 (`thermalCritical`) — グローバル

- `ProcessInfo.thermalState == .critical` が 60 秒継続したら安全のため全リースを失効
- これは無効化できない（安全機構）

### 7.6 総継続時間の上限 (`maxTotalDuration`) — グローバル

- リースが途切れずに繋がり続けた場合の、抑止全体の上限。既定 12 時間、無効化も可能
- クライアントがハートビートを打ち続ける限り TTL は延び続けるため、
  **「クライアントが正常に動いていても、いつかは必ず止まる」保証**がこれにあたる
- 上限到達の 30 分前に通知し、ワンクリックで延長できる

## 8. UI 仕様

### 8.0 UI 方針: 標準に任せる

最小要件を macOS 26 に切ったのは、**Liquid Glass に自前で追従しないため**（§4）。
この方針を UI 全体の制約として明示しておく。

- **素材・角丸・余白・影を自前で指定しない**。`.background()` に色を直接置いたり、
  独自の角丸カードを組んだりしない。標準コンテナに載せ、OS の描画に委ねる
- ポップオーバー・シート・リスト・フォーム・ツールバーはすべて SwiftUI 標準を使う。
  「思い通りの見た目にならない」を理由に独自描画へ逃げない
- 色はセマンティックカラー（`.primary`, `.secondary`, `.tint`）のみ。
  リテラルの色は、状態を表す最小限の箇所（抑止中を示すアクセント）に留める
- アイコンは SF Symbols。独自のアセットを持たない
- 結果として、将来 OS の見た目が変わっても**コードを変えずに追従する**

例外を作る場合は、その理由を設計判断（§16）に記録する。

### 8.1 メニューバー (`MenuBarExtra`)

常時表示。アプリの主導線。

**アイコン（テンプレート画像 / SF Symbols ベース）**

| 状態 | シンボル | 補足 |
| --- | --- | --- |
| `idle` | `moon.zzz` (outline) | 通常のスリープ可能状態 |
| `active` | `eye` (filled) | 抑止中 |
| `active` + 残り時間あり | `eye` + 残り時間テキスト | 「残り時間をメニューバーに表示」設定が ON のとき |
| `degraded` | `eye.trianglebadge.exclamationmark` | クラムシェル非対応で動作中 |
| エラー | `exclamationmark.triangle` | ヘルパー障害等 |

- アイコンは**状態が変わる瞬間だけ**アニメーション（うるさくしない）
- メニューバー幅を食わない選択肢として「アイコンのみ」モードを既定にする

**クリックメニュー**

```
┌────────────────────────────────────────┐
│  ● 抑止中 — あと 1時間 23分              │  ← ヘッダー（状態カード）
│    ふたを閉じてもスリープしません          │
│    バッテリー 68% · AC 接続中             │
├────────────────────────────────────────┤
│  リース (3)                              │
│   ● 手動           あと 1時間 23分   [×] │
│   ▸ build-runner   あと 28分   ↻     [×] │
│      テストスイート全体                   │
│   ▸ encoder        あと 12分   ↻     [×] │
│      素材の書き出し                       │
├────────────────────────────────────────┤
│  [ ■ すべて解除 ]                        │  ← 主アクション
├────────────────────────────────────────┤
│  自分のリースを延長  +30分 +1時間 +2時間  │
├────────────────────────────────────────┤
│  グローバル停止条件                       │
│   ✓ バッテリー 20% 以下                  │
│   ✓ 合計 12時間 で強制解除 (あと 9時間)   │
├────────────────────────────────────────┤
│  ウィンドウを開く…              ⌘0       │
│  設定…                         ⌘,       │
│  StayUp を終了                  ⌘Q       │
└────────────────────────────────────────┘
```

- リース行は **誰が持っているか**を最優先で見せる。`●` が対話的な要求、`▸` が外部クライアント。
  `↻` はハートビートで更新され続けていることを示し、直近の更新時に短くパルスする
  （要求元が生きていることが一目でわかる）
- クライアント名（`build-runner` 等）は `--owner` の値をそのまま表示する。
  アプリ側に既知の名前のリストは持たず、アイコンや色を名前で出し分けることもしない
- 各行の `[×]` でユーザーはいつでも個別に取り消せる。外部からの要求に対する最終的な決定権はユーザーにある
- リースが 0 件のときは主アクションが「開始する」になり、直下にプリセット
  （無期限 / 1時間 / 2時間 / 直前と同じ条件）が並ぶ
- リースが多いときはクライアント名ごとに畳む（`▸ build-runner (3)`）

- **Option キー押下**でメニューがデバッグ表示に切り替わる（`pmset -g` の生値、アサーション一覧、ヘルパーの状態、ログを開く）
- 状態カードは `MenuBarExtra(.window)` スタイルのカスタム SwiftUI ビューで実装し、リッチに見せる

### 8.2 ウィンドウ

`MenuBarExtra` だけでは足りない「設定」「履歴」「診断」を担う。`LSUIElement=true` なので Dock には出さず、ウィンドウを開いたときだけ `NSApp.setActivationPolicy(.regular)` に切り替える。

ウィンドウは `NavigationSplitView` によるサイドバーとコンテンツの二列構成にする。
macOS 26 のサイドバーとツールバーが提供する Liquid Glass を使い、独自のガラス背景は重ねない。

開始と全解除は、どの画面からでも同じ位置にあるツールバーの主操作とする。
開始期間は隣接するメニューから選び、コンテンツ内には同じ操作を重複させない。

**サイドバー構成**

| 項目 | 役割 |
| --- | --- |
| **概要** | 現在の抑止状態、残り時間、電源、安全な自動解除、実行中のセッションをまとめて確認する |
| **セッション** | クライアント、ラベル、開始時刻、残り TTL、バインド対象、更新回数を表で管理する |
| **履歴** | リース単位の開始と解除、解放事由、継続時間を監査する |
| **連携** | 外部クライアントの承認方針、承認済みクライアント、CLI の利用例を管理する |
| **設定** | 既定の期間、抑止範囲、安全な自動解除、履歴の保持期間を変更する |
| **診断** | ヘルパーの状態、`pmset` の生出力、緊急復元を扱う |

「概要」は状態の説明を先に示し、操作方法を覚えていない利用者でも次の行動を判断できる文言にする。
ヘルパーが未設定なら、ふたを閉じたときには効かないことと、設定への導線を一つの案内にまとめる。

「セッション」は行選択と Delete キーで個別に解除する。
行ごとに常設ボタンを並べず、選択中だけツールバーに解除操作を表示する。

「設定」と「連携」は macOS 標準の grouped Form を使う。
未実装の設定項目は表示せず、変更が実際の動作に反映される項目だけを提示する。

「診断」の緊急復元は通常操作と分離する。
緊急復元を実行すると、全リースを破棄して `disablesleep 0` への復元を試みる。

アプリを直接起動した場合は「概要」ウィンドウを表示する。
ウィンドウを閉じた後は Dock から退き、メニューバーで常駐を続ける。

### 8.3 その他の導線

| 導線 | 内容 |
| --- | --- |
| **グローバルホットキー** | `⌃⌥⌘1`、`⌃⌥⌘2`、`⌃⌥⌘3`、`⌃⌥⌘4` で30分、1時間、2時間、無期限のリースを開始し、`⌃⌥⌘0` ですべて解除 |
| **App Intents / Shortcuts** | `ToggleStayUpIntent` / `AcquireLeaseIntent(ttl:label:)` / `ReleaseAllIntent` / `GetStayUpStatusIntent` |
| **URL スキーム** | `stay-up://acquire?ttl=2h&owner=script` / `stay-up://release-all`。戻り値を取れないため補助的な位置づけ |

### 8.4 通知

`UNUserNotificationCenter`。すべて個別に ON/OFF 可能。既定は太字のみ ON。

| タイミング | 内容 | 既定 |
| --- | --- | --- |
| **未知のクライアントからの acquire** | 「"build-runner" がスリープ抑止を要求しています」+ 許可 / 今回のみ / 拒否 | **ON**（`clientPolicy: ask` 時） |
| **抑止が完全に解除された時** | 「スリープ抑止を解除しました（理由: バッテリー 20%）」 | **ON** |
| **グローバル条件による強制失効** | 「3 件のリースを強制解除しました（理由: 熱状態）」 | **ON** |
| **degraded で開始時** | 「ふたを閉じるとスリープします（ヘルパー未設定）」+ 設定を開くボタン | **ON** |
| **復元失敗時** | 「スリープ設定の復元に失敗しました」+ 手動復元ボタン | **ON** |
| 総継続時間の上限 30 分前 | 「あと 30 分で強制解除されます」+ 延長ボタン | ON |
| バッテリー事前警告 | 「バッテリー 25%。あと 5% で全解除されます」 | ON |
| 承認済みクライアントのリース取得/解放 | 「"build-runner" がリースを取得（30分）」 | OFF |
| 個別リースの TTL 失効 | — | OFF |
| 手動での取得/解放 | — | OFF |

- 通知は**まとめる**。複数リースが同時に失効しても 1 通に集約する。
  クライアントが頻繁に acquire/release する運用で通知の洪水にしない

## 9. 設定項目

| キー | 型 | 既定 | 説明 |
| --- | --- | --- | --- |
| `defaultDuration` | Duration? | `nil`（無期限） | 対話的リースの既定 TTL |
| `defaultBatteryThreshold` | Int? | `20` | バッテリー閾値（グローバル） |
| `maxTotalDuration` | Duration? | `12h` | 抑止の総継続時間の上限（グローバル） |
| `clientPolicy` | enum | `ask` | 外部クライアントからのリクエストの扱い。`ask` / `allow` / `deny` |
| `approvedClients` | [String] | `[]` | 承認済みのクライアント名 |
| `defaultClientLeaseTTL` | Duration | `30m` | 外部クライアントのリースの既定 TTL |

| `cliEnabled` | Bool | `true` | コントロールソケットを開くか |
| `keepDisplayAwake` | Bool | `false` | ディスプレイもスリープさせない |
| `preventDiskSleep` | Bool | `false` | ディスク省電力も抑止 |
| `showRemainingInMenuBar` | Bool | `false` | メニューバーに残り時間を表示 |
| `launchAtLogin` | Bool | `true` | ログイン時に起動（`SMAppService.mainApp`） |
| `autoStartOnLaunch` | Bool | `false` | 起動と同時に対話的リースを 1 つ取得 |
| `autoAcquireRules` | [Rule] | `[]` | 「プロセス名 X が起動していたらリースを保持する」規則。プロセス名バインドの自動版 |
| `restoreLeasesAfterReboot` | Bool | `false` | 再起動前に有効だった対話的リースを復帰時に再作成（外部クライアントのものは復帰しない） |

## 10. エラーハンドリング

| 事象 | 挙動 |
| --- | --- |
| ヘルパー未インストールで開始 | インストール案内シート。「今はアイドル抑止だけで開始」も選べる → `degraded` |
| CLI から acquire したがアプリ未起動 | CLI がアプリを起動して 5 秒待つ。失敗したら終了コード 4 とエラー JSON を返す |
| CLI から acquire したがヘルパー未設定 | リースは作る（`degraded`）。stderr に警告、終了コードは 0。**呼び出し元の処理は止めない** |
| `clientPolicy: ask` で承認待ちのまま応答なし | 30 秒でタイムアウトし拒否。CLI は終了コード 5 を返す。呼び出し元は処理を続行できる |
| クライアントが上限を超えて acquire | 拒否して終了コード 6。通知で「暴走の可能性」を伝え、その名前を一時的にブロックする選択肢を出す |
| 存在しない lease ID の renew / release | 終了コード 3。`release` は冪等扱いで警告のみ（既に失効しているのは正常なケース） |
| 同じリースファイルが二重に acquire される | `--if-not-exists` があれば既存 ID を返して成功。無ければエラー |
| リースファイルが手動で削除された | バインド解除として扱い、リースを解放 |
| ヘルパー登録をユーザーが拒否 | `degraded` で継続。以降は起動のたびには聞かず、メニューにバッジのみ |
| `pmset` が非 0 で終了 | セッション開始を中止し、アサーションも解放。エラーを状態カードに表示 |
| XPC 接続断（セッション中） | 3 回まで指数バックオフで再接続。復旧しなければ `degraded` に降格し通知 |
| 他ツールが `disablesleep=1` を設定済み | 開始時に検出し「StayUp 以外が設定しています」と表示。停止時は**元の値に戻す**（勝手に 0 にしない） |
| 起動時に `disableSleepSetAt` が残っている | StayUp 所有の孤児と判断して自動復元し、成功後に保存状態を消去する |
| 所有記録なしで `disablesleep=1` を検出 | 警告バナー + ワンクリック復元。自動復元はしない（他ツールの正当な設定を壊さないため） |
| 熱状態 critical | 強制停止（無効化不可） |
| ディスクフル等で履歴書き込み失敗 | リース制御は継続。履歴のみ失敗として `OSLog` に残す |
| `state.json` が壊れている / 読めない | 空の台帳として起動し、警告バナーを出す。`disablesleep=1` が残っていれば §10 の孤児として扱う |
| 履歴 JSONL の末尾行が途中で切れている | その行だけ読み飛ばす。それ以前の行は有効なものとして扱う |

## 11. 永続化とログ

### 11.1 方針: データベースを使わない

保存したいものは 2 つだけで、どちらも DB を必要としない。

| データ | 性質 | 形式 |
| --- | --- | --- |
| 現在のリース台帳 | 常に数件〜数十件。全体を丸ごと読み書きする | **JSON**（単一ファイル、原子的置換） |
| 履歴 | 追記のみ。読むのは「新しい順に必要な分だけ」 | **JSONL**（月次ローテーション） |

履歴に対して行う操作は「新しい順の走査」と「期間内の集計」だけで、
ランダムアクセスも結合も更新もない。**追記専用のログに対する逐次読み取り**という
アクセスパターンにはファイルがそのまま適合する。

- SQLite を入れるとスキーマ移行・ロック・WAL・破損復旧の面倒が増え、得るものが無い
- JSONL なら `tail`, `jq`, `grep` でそのまま読める。トラブルシュートが容易で、
  ユーザーが自分のデータを持ち出せる
- 将来的に件数が問題になるほど溜まるものではない（1 日数十行程度）

### 11.2 ファイル構成

```
~/Library/Application Support/StayUp/
├── state.json              現在のリース台帳（クラッシュ復帰・孤児検出用）
├── history/
│   ├── 2026-06.jsonl       月次ローテーション
│   └── 2026-07.jsonl
└── control.sock            CLI 用ソケット（§12.1）
```

**`state.json`** — 現在有効なリースのスナップショット

- リース台帳が変化したときだけ書く（renew では書かない）
- **一時ファイルに書いて `rename(2)`** で原子的に置換する。途中で落ちても壊れた state は残らない
- 用途は 2 つある
- 1 つ目は、アプリ再起動時に「前回どうなっていたか」を知ることである
- 2 つ目は、`disableSleepSetAt` を所有権の印として使い、StayUp が残した `disablesleep=1` だけを自動復元することである
- 起動時の復元判断には使うが、**リースを自動的に復活させることはしない**
  （`restoreLeasesAfterReboot` が有効な対話的リースを除く）

**`history/YYYY-MM.jsonl`** — 追記専用の監査ログ

```jsonl
{"ts":"2026-07-28T02:10:00Z","v":1,"event":"acquire","id":"01J...","client":"build-runner","kind":"external","pid":41153,"label":"テストスイート全体","ttl":1800,"binding":"pid:41153"}
{"ts":"2026-07-28T02:38:12Z","v":1,"event":"release","id":"01J...","reason":"bindingLost","duration":1692,"renewCount":14}
{"ts":"2026-07-28T02:38:12Z","v":1,"event":"suppressionEnded","duration":1692,"leaseCount":1}
```

- **1 行 1 イベント**。`event` は `acquire` / `release` / `suppressionStarted` / `suppressionEnded` /
  `globalStop` / `helperError` / `orphanDetected`
- **`renew` は行を書かない**。高頻度なので書くと肥大化する。
  更新回数と最終更新時刻は `release` 行に集約して記録する
- 各行に `v`（スキーマバージョン）を持たせ、読み取り側は未知のフィールドを無視する

### 11.3 書き込みの安全性

- **書き手はアプリ本体のみ**。ヘルパーも CLI もこれらのファイルには触らない。
  単一ライターなのでロックが要らない
- 追記は `O_APPEND` で開いたディスクリプタへの 1 回の `write(2)`。
  1 行を 4KB 未満に収めれば、追記は分割されない
- **読み取り時は壊れた行を読み飛ばす**。書き込み中の電源断で末尾行が欠けても、
  それ以前の行はすべて有効。ファイル全体が読めなくなることがない
- 履歴の書き込み失敗（ディスクフル等）でリース制御を止めない。§10 の通り記録のみ諦める

### 11.4 保持と集計

- `logRetentionDays` を超えた月次ファイルは起動時に削除する。ファイル単位なので削除が安価
- 履歴タブは**新しいファイルから逆順に、表示に必要な分だけ**読む。全件をメモリに載せない
- クライアント別・週次の集計は対象月のファイルだけを走査する。
  月次ローテーションが範囲を絞る役割を果たす

### 11.5 診断ログ

履歴（監査目的）とは別に、開発・障害調査用のログを持つ。

- `OSLog`（subsystem: `dev.tosaka.StayUp`）。カテゴリ: `lease`, `helper`, `power`, `socket`, `ui`
- ヘルパー側も同じ subsystem に出す（`log stream` で一体的に追える）
- 診断タブから `log show --predicate` 相当を実行してエクスポート
- こちらはファイルに永続化しない。OS のログシステムに任せる

### 11.6 記録しないもの

- バインド対象プロセスのコマンドライン引数全文。API キーや入力内容が乗りうる。
  プロセス名と PID のみに留める
- `--label` 以外のクライアント側の文脈。アプリはクライアントの内部事情を知らないし、
  知ろうともしない（§1 の設計原則）

## 12. CLI と外部クライアント連携

CLI は本アプリの中心的な導線のひとつ。GUI が「人間が見て操作する面」なら、CLI は
**プログラムが自分の必要に応じて抑止を要求する面**にあたる。

CLI の語彙はリース操作の一般語だけで構成し、特定のツールを想定した機能は持たない（§1 の設計原則）。

### 12.1 通信方式

アプリに `stay-up` CLI を同梱する（`StayUp.app/Contents/MacOS/stay-up`）。

- CLI は**自前で `pmset` を叩かない**。真実の源を二重化しないため、必ずアプリに委譲する
- 通信は **Unix ドメインソケット**（`~/Library/Application Support/StayUp/control.sock`, mode 0600）。
  リクエスト/レスポンス型で、`--json` の戻り値やリース ID をそのまま受け取れる
- ソケットが無い / 接続できない場合、CLI が `StayUp.app` を起動して最大 5 秒待ってから再試行する
- ソケットのパーミッションとオーナー UID を接続時に検証する。他ユーザーからの操作は受け付けない

> URL スキーム（`stay-up://`）も併せて提供するが、戻り値を取れないため片方向の通知用途に限る。
> 外部クライアント連携の主経路はソケット。

### 12.2 コマンド

```
# --- リース操作（外部連携の中心） ---
stay-up run [opts] -- <command...>   # コマンドの実行中だけ抑止。終了コードは透過
stay-up acquire [opts]               # リースを取得し、lease ID を stdout に出す
stay-up renew <id|--lease-file F> [--ttl 30m]
stay-up release <id|--lease-file F>
stay-up list [--json]                # 有効なリース一覧（誰が・いつから・あと何分）

# --- 状態 ---
stay-up status [--json]              # 全体状態。人間可読 / 機械可読
stay-up wait                         # 全リースが消えるまでブロック（スクリプト用）
stay-up doctor                       # ヘルパー・権限・pmset の診断と修復提案

# --- awake.sh 互換 ---
stay-up                              # 引数なしはトグル
stay-up start -t 1h -b 20            # ユーザー起源リースを 1 つ取る
stay-up stop                         # ユーザー起源リースを全て解放
```

**`acquire` の主なオプション**

| オプション | 説明 |
| --- | --- |
| `--ttl 30m` | TTL。外部クライアントでは**必須**（既定 30 分） |
| `--bind-pid <pid>` / `--bind-pid $$` | PID にバインド。消滅で自動解放 |
| `--lease-file <path>` | リースファイルを作成し、それにバインド。ID をファイルに書くので後続コマンドが ID を持ち回らなくて済む |
| `--owner <name>` | クライアント名。UI・履歴・ポリシー適用のキーになる自由文字列。アプリは中身を解釈しない |
| `--label "auth のリファクタ"` | 人間可読な説明 |
| `--reason ...` | 承認プロンプトに出す理由 |
| `--if-not-exists` | 同じ `--lease-file` のリースが既にあれば何もせず成功（冪等） |

**最も推奨する形**

```bash
stay-up run --owner build-runner --label "テストスイート全体" -- npm test
```

プロセスの生存がそのままリースの生存なので、**解放漏れが原理的に起きない**。
クラッシュしても、`kill -9` されても、リースは消える。
ドキュメントで最初に案内すべき形はこれ。

### 12.3 利用パターン

`stay-up` の使い方は 3 つに整理できる。用途に応じてどれかを選ぶ。

**(a) コマンドを包む** — 最も安全。可能なら常にこれ

```bash
stay-up run --owner backup -- restic backup ~/work
```

**(b) PID にバインドする** — 既に動いているプロセスや、シェル自身に紐づける

```bash
stay-up acquire --owner my-script --bind-pid $$ --ttl 1h
# 以降このシェルが生きている間だけ抑止される
```

**(c) ハートビート** — 開始と終了のイベントが取れるが、プロセスに紐づけられない場合

```bash
# 開始時（冪等）
stay-up acquire --owner my-tool --if-not-exists --ttl 30m \
  --lease-file ./.stay-up-lease --label "long task"

# 進捗があるたびに（TTL を延ばす）
stay-up renew --lease-file ./.stay-up-lease --ttl 30m

# 終了時
stay-up release --lease-file ./.stay-up-lease
```

(c) の要点は、**終了処理が実行されなくても安全である**こと。
ハートビートが止まれば TTL で自然に失効するので、`release` は「早く解放するための最適化」でしかない。
異常終了・強制終了・クラッシュのいずれでも、最悪 30 分で回収される。

- `--lease-file` を使うと、後続コマンドがリース ID を持ち回らなくて済む。
  作業ディレクトリごとにファイルを分ければ、**並走しても互いを解除しない**
- `--if-not-exists` により、再実行や再接続で二重取得しない
- `renew` は 1 回あたり数ミリ秒（§13）。高頻度に叩いても呼び出し側の速度に影響しない

具体的なツールへの繋ぎ込み方は付録 A に例を置く。**CLI 側にツール固有の機能は持たせない。**

### 12.4 外部に権限を渡すことへの防御

外部プロセスが状態を書き換えられるということは、
**「Mac をスリープさせない権限」を外部に委譲する**ということ。
バグ・無限ループ・release 忘れが、そのまま「一晩中スリープしない Mac」になりうる。多層で防ぐ。

| 層 | 仕組み |
| --- | --- |
| **TTL 必須** | 外部クライアントのリースに無期限を許さない。既定 30 分、`maxClientLeaseTTL`（既定 2 時間）で上限 |
| **ハートビート必須** | 更新が止まれば失効する。要求元が死ねば自動的に解除される |
| **承認モード** | `clientPolicy`: `ask`（初出のクライアント名ごとに通知で承認）/ `allow` / `deny`。既定は `ask` |
| **クライアント許可リスト** | 承認済みの名前を記録。未知の名前からの acquire は通知して承認を求める |
| **同時リース数の上限** | `maxLeasesPerClient`（既定 8）。無限に acquire を繰り返す暴走を止める |
| **グローバル拒否権** | バッテリー・熱・総継続時間の条件はリースより強い（§7.6）。外部からは解除できない |
| **権限の非対称性** | 外部クライアントは**自分と同じ名前のリースしか release できない**。対話的リースには触れない |
| **可視性** | 有効なリースは常にメニューバーとウィンドウに一覧表示され、ユーザーはいつでも個別に取り消せる |
| **監査** | 全ての acquire / release をクライアント名付きで履歴に記録する（§11.2） |

`deny` に設定すれば、CLI は状態を書き換えられず `status` / `list` のみになる。読み取り専用の運用も選べる。

> **クライアント名は認証ではない**。`--owner` は自己申告の文字列で、詐称できる。
> これは「意図しない抑止をユーザーに気づかせ、取り消せるようにする」ための識別であって、
> 悪意ある動作を防ぐ機構ではない。ソケットに接続できる時点で同一ユーザー権限なので、
> それ以上の防御は意味を持たない。この前提を UI でも誤解させない。

### 12.5 状態の読み取り（プロンプト・ステータスライン）

`stay-up status --json` を安定した契約として提供する。

```json
{
  "state": "active",
  "capability": "full",
  "leaseCount": 2,
  "activeSince": "2026-07-28T02:10:00Z",
  "endsAt": "2026-07-28T04:10:00Z",
  "endsReason": "ttl",
  "leases": [
    { "id": "01J...", "owner": "build-runner", "kind": "external",
      "label": "テストスイート全体",
      "expiresAt": "2026-07-28T02:40:00Z", "binding": "pid:41153" }
  ],
  "battery": { "percent": 68, "source": "ac" },
  "warnings": []
}
```

- tmux ステータスライン / Starship / Ghostty のタイトルから使える
- 高頻度で叩かれる想定なので、`status` はソケット越しのキャッシュ読み取りのみで、`pmset` を都度実行しない
- スキーマにバージョンを持たせ、破壊的変更をしない

### 12.6 `awake.sh` からの移行

- `awake.sh` のフラグ（`-t`, `-b`, `start`, `stop`, `status`）を互換で受け付け、移行コストをゼロにする
- 設定から `~/.local/bin/stay-up` へのシンボリックリンク作成を実行。`nixos-config` からも管理できるようにする
- **エイリアス**: `awake` と `stayup`（ハイフン無し）のシンボリックリンクも任意で作成できる。
  正式名は `stay-up` だが、手で打つには `awake` が短く、既存のシェル履歴やスクリプトもそのまま動く

## 13. 非機能要件

| 項目 | 要件 |
| --- | --- |
| アイドル時 CPU | 実質 0%。ポーリングを使わず、電源・プロセスの通知でイベント駆動する。UI 更新用のタイマーはメニューを開いている間のみ 1Hz |
| **CLI の応答時間** | `renew` / `status` は **50ms 以内**（プロセス起動込み）。ハートビートとして高頻度に呼ばれるため、ここが遅いと呼び出し元全体が遅くなる。CLI 本体は Swift の軽量バイナリとし、重い初期化をしない |
| **`stay-up run` のオーバーヘッド** | 起動〜子プロセス exec まで 30ms 以内。終了コード・シグナル・stdio を完全に透過する |
| メモリ | 常駐時 50MB 以下 |
| 起動時間 | ログイン項目としての起動で 300ms 以内にメニューバーへ表示 |
| 配布 | Developer ID 署名 + Notarization。Sparkle による自動更新。Homebrew Cask も用意 |
| ヘルパー更新 | アプリ更新時にヘルパーのバージョンを比較し、必要なら再登録。バージョン不一致時は起動を拒否して案内 |
| ローカライズ | 日本語 / 英語 |
| アクセシビリティ | メニューバーアイコンに状態を含む VoiceOver ラベル。色だけで状態を表現しない |
| Nix 連携 | `nixos-config` の home-manager から Cask / 設定を管理できるようにする（`awake.sh` の置き換え先として） |

## 14. 要検証事項

実装前に検証が必要な、設計の前提を揺るがしうる項目。

1. **`SMAppService.daemon` + XPC の切断検知の信頼性**
   クライアントを `SIGKILL` したときに、ヘルパー側の `invalidationHandler` が確実に発火するか。
   発火しないケースがあれば heartbeat ウォッチドッグ（層 5）を主機構に格上げする。

2. **Apple Silicon のクラムシェル挙動**
   外部ディスプレイ・電源なしでふたを閉じた状態で、`disablesleep=1` が本当にスリープを防ぐか。
   Intel と挙動が違う可能性、および OS バージョンによる差分を実機確認する。

3. **ふた閉じ時のサーマルスロットリング**
   閉じた状態で長時間 CPU を回すと放熱が厳しい。§7.5 の閾値（critical 60 秒）が妥当か実測する。

4. **CLI の起動時間**
   `renew` はハートビートとして高頻度に呼ばれるため、CLI プロセスの起動〜応答が 50ms を超えると
   呼び出し元の体感が悪化する。Swift バイナリの実測が必要。
   超えるなら、ハートビートの手段を `renew` コマンドではなく
   「リースファイルの mtime を `touch` するだけ」に変え、アプリ側が FSEvents で拾う方式を追加する
   （外部プロセスの起動すら不要になる）。

5. **ログアウト・再起動時の復元タイミング**
   `NSWorkspace.willPowerOffNotification` から `pmset` 実行完了までに OS が待ってくれるか。
   間に合わないなら層 4（ヘルパー起動時の孤児チェック）が唯一の砦になる。

## 15. 実装フェーズ

| フェーズ | 内容 | 完了条件 |
| --- | --- | --- |
| **P0: 検証** | §14 の 2〜4 を最小コードで確認 | 復元機構の主方式と Apple Silicon での挙動が確定する |
| **P1: コア** | `SessionManager` + `LeaseRegistry` + `AssertionController` + ヘルパー + XPC + 復元保証（層 1〜4） | テストから複数リースの取得/解放ができ、`SIGKILL` しても復元される |
| **P2: メニューバー** | `MenuBarExtra`、状態カード、リース一覧、TTL/バッテリー条件、通知 | `awake.sh` の全機能が GUI で使える |
| **P3: CLI と外部連携** | `ControlSocket`、`stay-up run` / `acquire` / `renew` / `release` / `status --json`、`ClientPolicy` | 外部プロセスから抑止が自動制御され、release 忘れが TTL で回収される |
| **P4: ウィンドウ** | 状態 / 履歴 / 設定 / クライアント / 診断タブ | 誰がいつ Mac を起こしていたかを追跡でき、緊急復元が GUI で完結する |
| **P5: 外部導線** | App Intents / Shortcuts / グローバルホットキー / URL スキーム / `awake.sh` 互換 | `awake.sh` を削除できる |
| **P6: 配布** | 署名・Notarization・Sparkle・Homebrew Cask・ローカライズ・付録 A の利用例整備 | 他人が入れられる |

P1〜P2 で `awake.sh` の機能的等価物に到達する。**P3 が本アプリ固有の価値**で、
「プログラムが自分で必要な時だけ Mac を起こし、終わったら勝手に戻す」が成立する。
P3 を P4 より先に置いているのはこのため。

## 16. 設計判断の記録

| 判断 | 理由 | 却下した代替案 |
| --- | --- | --- |
| root ヘルパーを常駐 LaunchDaemon にする | 1 度の承認で以降は認証不要にし、かつ**接続断による自動復元**という安全性を得るため | 都度 `AuthorizationExecuteWithPrivileges`（非推奨・毎回認証・復元保証なし） |
| `pmset` を叩く（プライベート API を使わない） | 将来の OS 更新で壊れにくく、`awake.sh` と挙動が完全に一致する | `IOPMSetSystemPowerSetting` 等のプライベート API |
| ディスプレイスリープは既定で抑止しない | ふた閉じ運用が主目的で、画面を点けておく理由がない。省電力と焼き付き防止 | `caffeinate -d` 相当を常時 ON |
| 単一セッションではなく参照カウント式のリース | クライアントの並走とユーザー操作の共存を壊さないため。片方が終わっただけで全体が解除される事故を防ぐ | グローバルなオン/オフ 1 つ |
| リース単位とグローバルの 2 層に条件を分ける | 外部に委譲した権限に対して、ユーザー側が必ず勝てる拒否権を残すため | すべての条件を対等に扱う |
| 外部クライアントのリースに TTL を必須にする | 「要求元が死んだら自然に解除される」を仕組みで保証する。release 忘れを性善説に頼らない | 無期限を許し、release を信頼する |
| `Client` を interactive / external の 2 ケースに留める | 振る舞いの差を生む本質的な区別だけを型にする。それ以外は表示用の文字列で足りる | ツールの種別ごとにケースを持つ |
| 特定ツールの設定ファイルを書き換える機能を作らない | ツール側の設定形式に追従し続ける保守コストを負わない。汎用ツールがツールの数だけ知識を持ち始めると破綻する | `install-hooks` のような統合コマンド |
| CLI の失敗で呼び出し元を止めない | 抑止は本来の作業の付随物。ヘルパー未設定や承認拒否で `npm test` が落ちるのは本末転倒 | 失敗時に非 0 を返して中断させる |
| 永続化に DB を使わず JSON / JSONL にする | 追記と逐次読み取りしかしないアクセスパターンにファイルが適合する。スキーマ移行・ロック・破損復旧のコストを負わない | SQLite、Core Data |
| `renew` を履歴に記録しない | 高頻度なので書くと肥大化する。更新回数を `release` 行に集約すれば情報は失われない | 全イベントを 1 行ずつ記録 |
| 履歴を月次ファイルにローテーションする | 保持期限切れの削除がファイル単位で済み、期間集計の走査範囲も絞れる | 単一ファイル + 行単位の削除 |
| 停止条件は OR 評価 | `awake.sh` の挙動を踏襲。「安全側に倒す」= どれか 1 つでも該当したら止める | AND 評価、条件ごとの優先度 |
| 孤児の `disablesleep=1` を自動復元しない | 他ツールが正当に設定している可能性がある。勝手に他人の設定を壊さない | 起動時に無条件で 0 にする |
| CLI は自前で `pmset` を叩かない | 状態の真実の源を 1 つに保つ。CLI と GUI で別々のリース台帳が走る事態を防ぐ | CLI をスタンドアロンにする |
| CLI とアプリの通信に UNIX ドメインソケットを使う | 双方向のリクエスト/レスポンスが要る（lease ID を返す、`status --json` を返す）。短命な CLI プロセスから軽量に接続できる | URL スキーム（戻り値が取れない）、ファイル経由のポーリング |
| 初期リリースでコントロールセンター対応をしない | 3rd party に許されるのは button / toggle のみで展開パネルの API が無く、単なる ON/OFF ボタンにしかならない。ウィジェット拡張の別プロセス化に見合う価値が出ない。即時性はホットキーで満たせる | 最初から `ControlWidget` を用意する |
| ただし `AppIntent` は最初から実装する | 後からコントロールセンターに対応する場合、その `AppIntent` を包むだけで済む。将来の追加を妨げないための最小の布石 | UI から直接 `SessionManager` を呼ぶ |
| 最小要件を macOS 26 にする | UI を標準コンポーネントだけで組み、Liquid Glass に自動追従させたい。下位互換のために見た目を 2 系統保守するのは、個人利用が出発点のツールに見合わない | macOS 14〜15 も対象にする |

## 付録 A. 利用例

**この付録は実装対象ではない。** ドキュメントとして提供するレシピ集であり、
ここに書かれた個々のツールについてアプリが知識を持つことはない（§1 の設計原則）。
すべて §12.2 の汎用コマンドの組み合わせで表現されている。

### A.1 コマンドを包む

```bash
stay-up run --owner build -- make release
stay-up run --owner backup -- restic backup ~/work
stay-up run --owner encode -- ffmpeg -i in.mov out.mp4
```

Makefile に組み込む場合：

```makefile
release:
	stay-up run --owner build --label "release build" -- $(MAKE) _release
```

### A.2 シェルスクリプトの中で使う

```bash
#!/usr/bin/env bash
set -euo pipefail

# このスクリプトが生きている間だけ抑止する
stay-up acquire --owner my-pipeline --bind-pid $$ --ttl 2h \
  --label "nightly pipeline" >/dev/null || true   # 失敗しても処理は続ける

./step1.sh
./step2.sh
```

`--bind-pid $$` により、`set -e` で途中終了しても、`kill` されてもリースは消える。
`trap` による後始末は不要。

### A.3 開始・終了フックを持つツールと繋ぐ

セッションの開始と終了でコマンドを実行できるツールなら、§12.3 (c) のハートビート方式が使える。
以下は coding agent（Claude Code）のフック設定を例にしたもの。
**他のツールでも、開始 / 進捗 / 終了に相当するイベントに同じ 3 つのコマンドを割り当てればよい。**

```json
{
  "hooks": {
    "SessionStart": [{ "hooks": [{ "type": "command",
      "command": "stay-up acquire --owner claude-code --if-not-exists --ttl 30m --lease-file \"$CLAUDE_PROJECT_DIR/.stay-up-lease\" --label \"$(basename \"$CLAUDE_PROJECT_DIR\")\" || true" }]}],

    "PostToolUse": [{ "hooks": [{ "type": "command",
      "command": "stay-up renew --lease-file \"$CLAUDE_PROJECT_DIR/.stay-up-lease\" --ttl 30m || true" }]}],

    "SessionEnd": [{ "hooks": [{ "type": "command",
      "command": "stay-up release --lease-file \"$CLAUDE_PROJECT_DIR/.stay-up-lease\" || true" }]}]
  }
}
```

- 進捗イベント（ここでは `PostToolUse`）がハートビートになり、動いている間だけ TTL が延びる
- 終了イベントが発火しなくても 30 分で自然に失効するので、後始末の信頼性に依存しない
- プロジェクトごとに `.stay-up-lease` が分かれるため、並走しても互いを解除しない
- `|| true` を付け、抑止の失敗が本来の作業を止めないようにする

`.stay-up-lease` は `.gitignore` に加えておく。

### A.4 状態をプロンプト・ステータスラインに出す

```bash
# tmux status-right
stay-up status --json | jq -r 'if .state=="active" then "☕ \(.leaseCount)" else "" end'
```

`status` はキャッシュ読み取りのみなので、高頻度に呼んでも負荷にならない（§12.5）。

### A.5 履歴を直接調べる

JSONL なので専用ツールが要らない（§11.2）。

```bash
cd ~/Library/Application\ Support/StayUp/history

# 今月、どのクライアントが何回リースを取ったか
jq -r 'select(.event=="acquire") | .client' 2026-07.jsonl | sort | uniq -c | sort -rn

# 6 時間以上続いたリースを探す
jq -r 'select(.event=="release" and .duration > 21600)' 2026-07.jsonl

# 想定外の解除事由を洗い出す
jq -r 'select(.event=="release") | .reason' 2026-07.jsonl | sort | uniq -c
```
